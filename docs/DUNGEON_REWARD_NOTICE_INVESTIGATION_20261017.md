# Dungeoneering reward notice vs next-floor countdown — 17 October 2026

Scope: one solo small complexity-1 floor-1 completion, from the boss death to the reward notice, through the 30 s next-floor countdown. Target: `/home/kannibalkiwi/orca/projects/SoloScape`. No production source, data, cache, or save was changed, and no patch was exported. The test file is in the ignored `upstream/game-server` checkout.

## Result

**Negative reproduction (red, opt-in):** the reward notice is left unanswered past the countdown. The next dungeon replaces the map, the notice closes, and the reward is never delivered. XP, tokens, floor 1 credit, and `dungeon_reward_given` all stay at zero, and the later click does nothing.

**Positive control (green):** the same notice, acknowledged before the countdown ends, delivers the reward: XP 0 → 201.0, tokens 0 → 20, `dungeon_reward_given` true, floor 1 ticked off.

This is worse than the audit's F2 hypothesis (the reward may be committed after the next dungeon is generated). In this run the reward is dropped, not late.

## Source backing

Read-only inspection, under `upstream/game-server/`. Labels: **[Source]** read in the cited lines, **[Observed]** from the test run, **[Inferred]** a conclusion not separately proven.

1. **[Source]** The reward is inside `strongQueue("dungeon_info")` (`game/src/main/kotlin/content/skill/dungeoneering/DungeonComplete.kt:198-199`). The notices are `item(3032, …)` at `:292`, `:297`, `:299`, `:305`. Each suspends the queue on `pauseButton()` (`engine/.../suspend/Suspend.kt:35-37`, `Suspension.Continue`). The reward flag, XP, and tokens come after the notices, at `:309`, `:311`, and the token `inc`.
2. **[Source]** `End-dungeon` calls `continueCountDown(leader)` at `DungeonComplete.kt:49` without waiting for the queue, so the 30 s timer starts immediately.
3. **[Source]** The next dungeon is generated by `timerStop("dungeon_continuation")` → `generate(…)` (`game/src/main/kotlin/content/area/wilderness/daemonheim/DungeonEntrance.kt:108`, `:219` `member.closeInterfaces()`).
4. **[Source]** `closeInterfaces()` → `closeDialogue()` (`engine/.../client/ui/Interfaces.kt:283-285`) sets `suspension = null` when it is `Suspension.Continue`, without resuming it. The suspended `dungeon_info` coroutine is then never resumed.
5. **[Source]** `DungeoneeringParty.clear` (`DungeoneeringParty.kt:326` `player.queue.clear()`, called from `DungeonEntrance.kt:240`) does not reach the reward. `ActionQueue` removes an action from its list when it launches (`engine/.../queue/ActionQueue.kt:50`, `:82`), so the suspended reward is not in the queue to clear. `queue.contains("dungeon_info")` returns false even at notice-open, which is why a queue probe was not used.
6. **[Observed]** At the moment the map is replaced, `suspension` goes from `Continue` to `none` and the notice closes at the same time, with no reward. This matches steps 3–4.
7. **[Inferred]** The loss mechanism is step 4: the `Continue` suspension is cleared without resuming the `dungeon_info` coroutine, so the rest of the reward block never runs. No debugger or stack trace was taken, so the exact call that clears it is read from source, not captured.

Relation to the audit: F2 (`docs/DUNGEONEERING_COMPLETION_AUDIT_20261017.md`) said the reward is queued and may run after the countdown. This run shows the queued reward is discarded when the next dungeon is generated with the notice still open. The `dungeon_reward_given` guard does not help, because the flag is set only inside the block that never runs.
